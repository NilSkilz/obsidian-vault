### Uptime Kuma — public-monitor flapping (up/down Telegram spam)
Rob: "still getting stuff going up/down on kuma." Diagnosed end to end.
- **Only the 5 `(public)` HTTPS monitors flap** (Vaultwarden/Tide/Plex/Plausible/GlitchTip). All 16 internal/direct monitors: zero events, rock solid. Every failure is `timeout of 48000ms exceeded` then straight back to 200/401.
- Ruled out yesterday's DNS tail: `86.181.171.46` now gone from every resolver (1.1.1.1/8.8.8.8/UDM all clean). Ruled out IPv6: from inside the Kuma container IPv6 fails *fast* (ENETUNREACH 33ms), and Node resolves IPv4-first anyway.
- Real cause: the public monitors hit Kuma → Cloudflare edge → back to the home WAN (109.149.184.92) → NPM (a **hairpin/NAT-loopback** round trip). Measured IPv4 latency to the public path swinging 0.35s–4.4s and occasionally hanging to the full timeout. The path genuinely drops for ~2-3 min at a time, intermittently. Services themselves never blink.
- **`maxretries` was already 2** (my first API read used the wrong key `retries` and showed None — the real field is `maxretries`; kwarg is `maxretries`, `retries=` is silently ignored). So the DOWN events had *already* survived 2 retries → these are genuine multi-minute hairpin drops, not single-beat twitchiness.
- **Fix applied** (via `~/.local/share/kuma-venv` + uptime-kuma-api): public monitors now `maxretries=4, timeout=20s, retryInterval=30s` (was 2 / 48s / 60s). Rides out the transient hairpin blips (~4 min tolerance) while still catching a real sustained outage. Internal monitors left untouched (never flap).
- Open option for Rob: a monitor testing the full external chain *from inside the house* is noisy by design. If he wants true external checks, needs an off-LAN vantage (Kuma 1.x has no remote agent) or accept the hairpin noise. Current tuning should stop the phone spam.
